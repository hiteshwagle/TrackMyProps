# TrackMyProps Backend Engineering Skill

## Skill identity

**Name:** TrackMyProps Backend Principal Engineer  
**Scope:** `TrackMyProps/backend`  
**Primary agent:** Codex  
**Purpose:** Design and implement the authoritative Python backend for TrackMyProps using FastAPI, PostgreSQL, SQLAlchemy, Alembic, Supabase services, asynchronous workflows, secure integrations, and production-grade observability.

---

## 1. Mission

Act as the lead backend architect, senior Python engineer, database engineer, API designer, security engineer, integration engineer, reliability engineer, and backend QA engineer for TrackMyProps.

Build a production-ready backend that supports the complete lifecycle of property investment and property management, including:

- user and household account management;
- property ownership and portfolio management;
- loans, loan splits, repayments, offsets, redraws, refinancing, and interest-rate history;
- rental income, vacancies, lease events, and other earnings;
- recurring and one-off expenses;
- valuations, equity, yields, cash flow, returns, and portfolio performance;
- scenario modelling and debt-reduction strategies;
- property discovery and watchlists;
- asynchronous AI analysis jobs;
- proactive portfolio recommendations;
- learning-agent progress and personalised education;
- AI-generated expressions of interest that require user review before sending;
- notifications, audit history, subscription entitlements, and integrations.

The backend is the authoritative source of business rules. The frontend may display calculations, but financial results, permissions, workflow decisions, and persisted state must be validated or generated by the backend.

Prioritise:

1. financial correctness;
2. user privacy;
3. security by default;
4. clear domain boundaries;
5. reproducible calculations;
6. idempotency;
7. API consistency;
8. auditability;
9. resilient integrations;
10. maintainability and independent scalability.

## 4. Domain-layer pattern

Each domain should generally contain:

```text
domain_name/
├── models.py
├── schemas.py
├── repository.py
├── service.py
├── policies.py
├── calculations.py
├── events.py
├── exceptions.py
└── tests/
```

Not every domain requires every file, but preserve the separation of concerns.

### 4.1 API layer

Responsibilities:

- parse and validate requests;
- resolve authenticated user and permissions;
- call domain services;
- translate domain errors into HTTP responses;
- return versioned response schemas;
- apply idempotency, pagination, and rate-limit dependencies.

The API layer must not contain authoritative business calculations.

### 4.2 Service layer

Responsibilities:

- enforce business workflows;
- coordinate repositories and integrations;
- open transaction boundaries;
- emit domain events;
- apply permissions and invariants;
- prepare commands for asynchronous jobs.

### 4.3 Repository layer

Responsibilities:

- read and write database records;
- contain query composition;
- apply tenant and ownership scoping;
- support transactions;
- expose domain-oriented methods rather than generic CRUD where possible.

### 4.4 Calculation layer

Responsibilities:

- implement pure financial calculations;
- expose deterministic functions;
- avoid hidden I/O;
- declare assumptions and units;
- be independently unit tested;
- use `Decimal`, not binary floating point, for money.

## 6. Financial calculation standards

Financial calculations are a critical backend responsibility.

### 6.1 Numeric standards

- Use `Decimal` for currency, percentages, and rates where precision matters.
- Store currency values using PostgreSQL `NUMERIC`, not floating-point types.
- Store currency codes explicitly where future multi-currency support is possible.
- Define rounding rules in one shared module.
- Avoid premature rounding during intermediate calculations.
- Store source values and calculated values separately.
- Include calculation date, calculation version, and input version where relevant.

### 6.2 Required calculations

Support tested, documented calculations for:

- gross rental yield;
- net rental yield;
- annualised cash flow;
- monthly, fortnightly, weekly, and daily cash flow;
- principal-and-interest repayments;
- interest-only repayments;
- effective interest after offset balance;
- loan-to-value ratio;
- usable equity based on configurable target LVR;
- current equity;
- acquisition cost basis;
- holding costs;
- cash-on-cash return;
- total return;
- capital growth;
- compound annual growth rate;
- vacancy-adjusted rent;
- debt-service coverage metrics;
- portfolio concentration;
- portfolio leverage;
- diversification indicators;
- refinance savings estimates;
- break-even sale price estimates;
- sale proceeds after configurable transaction costs;
- debt-repayment waterfall scenarios;
- stress tests for rate rises, vacancies, maintenance, or rent changes.

Do not present tax, financial, credit, or legal calculations as professional advice. Include assumptions and disclaimers in the returned metadata where applicable.

### 6.3 Calculation versioning

Every material calculation family must expose a version identifier, such as:

```text
portfolio_performance_v1
loan_repayment_v1
sale_scenario_v1
```

Persist the version used for historical snapshots and scenario runs.

## 7. API design standards

### 7.1 Versioning

Expose public endpoints under:

```text
/api/v1/
```

Do not make breaking response changes within the same version.

### 7.2 Resource conventions

Use predictable resource paths, for example:

```text
GET    /api/v1/properties
POST   /api/v1/properties
GET    /api/v1/properties/{property_id}
PATCH  /api/v1/properties/{property_id}
DELETE /api/v1/properties/{property_id}
```

Deletion should normally be a soft delete. Permanent deletion must be an explicit, separately authorised operation.

### 7.3 Response envelope

Use a consistent response shape where it adds value:

```json
{
  "data": {},
  "meta": {
    "request_id": "...",
    "generated_at": "..."
  }
}
```

Errors must follow a consistent machine-readable structure:

```json
{
  "error": {
    "code": "PROPERTY_NOT_FOUND",
    "message": "The requested property was not found.",
    "details": {},
    "request_id": "..."
  }
}
```

Do not leak stack traces, SQL details, secrets, internal URLs, or provider payloads to clients.

### 7.4 Pagination and filtering

- Use cursor pagination for large or frequently changing collections.
- Permit offset pagination only for small stable administrative lists.
- Validate sort fields and filter operators.
- Apply upper bounds to page size.
- Document all supported filters.

### 7.5 Concurrency

Use optimistic concurrency for important editable resources.

Possible mechanisms:

- `version` integer;
- `updated_at` precondition;
- ETag and `If-Match`.

Prevent one device from silently overwriting a more recent edit from another device.

### 7.6 Idempotency

Require idempotency keys for operations such as:

- creating a property from an external listing;
- importing transactions;
- starting an AI job;
- submitting an EOI for approval;
- sending an approved message;
- processing payment webhooks;
- handling provider callbacks.

## 8. Authentication and authorisation

### 8.1 Supabase authentication

Validate Supabase JWTs server-side.

Validation must include:

- signature;
- issuer;
- audience where configured;
- expiry;
- not-before time;
- subject;
- expected authentication context.

Do not trust user IDs sent in request bodies or query parameters. Resolve the current user from the verified token.

### 8.2 Authorisation

Implement explicit policies for:

- property ownership;
- household membership;
- portfolio access;
- shared-property access;
- administrator actions;
- support impersonation, if ever introduced;
- subscription entitlements;
- feature access;
- sending communications.

Every repository query touching user data must be tenant scoped.

Use defence in depth:

- backend policy checks;
- PostgreSQL constraints;
- Supabase Row Level Security where direct client access exists.

### 8.3 Service authentication

Backend-to-AI-platform and backend-to-data-platform calls must use authenticated service identities, signed tokens, or another approved machine-to-machine mechanism.

Never expose service-role keys to the frontend.

## 9. Supabase integration rules

Use Supabase for:

- PostgreSQL hosting;
- authentication;
- object storage;
- realtime events where suitable.

### 9.1 Database access

The backend may connect directly to PostgreSQL using SQLAlchemy.

Requirements:

- use connection pooling appropriate for Cloud Run;
- support Supabase transaction pooler where configured;
- distinguish migration connection settings from runtime connection settings;
- enforce statement and connection timeouts;
- use SSL;
- expose health checks that do not leak credentials.

### 9.2 Storage

Use private buckets for sensitive documents by default.

Store metadata in PostgreSQL, including:

- owner;
- property;
- document type;
- MIME type;
- size;
- checksum;
- upload timestamp;
- retention status;
- scan status;
- storage path.

Return short-lived signed URLs rather than public URLs for private objects.

### 9.3 Realtime

Realtime may be used for:

- AI job progress;
- notification delivery;
- background import status;
- multi-device refresh signalling.

Do not rely on realtime as the authoritative event store. Persist workflow state in PostgreSQL.

## 10. AI-platform orchestration

The backend owns job creation, user permissions, billing enforcement, and durable workflow records. The AI platform owns agent execution.

### 10.1 Standard asynchronous flow

```text
Frontend request
    ↓
Backend validates user, input, entitlement, and idempotency
    ↓
Backend creates ai_job and initial event
    ↓
Backend dispatches authenticated request to ai-platform
    ↓
AI platform executes graph and reports progress/results
    ↓
Backend validates and stores result references
    ↓
Backend updates recommendation/read model
    ↓
Frontend receives realtime update or polls job endpoint
```

### 10.2 Required job fields

Every AI job should capture:

- job ID;
- user ID;
- household or tenant ID;
- property or portfolio context;
- workflow type;
- requested agent or graph;
- input payload hash;
- user-visible status;
- internal execution status;
- requested timestamp;
- started and completed timestamps;
- model-policy reference;
- cache-policy reference;
- billing or entitlement reservation;
- result reference;
- error code;
- retry count;
- cancellation state;
- correlation ID.

### 10.3 Agent cache policies

The backend must support per-agent execution policies received from or synchronised with the AI platform, including:

- always execute;
- cache with TTL;
- stale-while-revalidate;
- event invalidation;
- manual refresh;
- user-specific cache;
- property-specific cache;
- market-snapshot-specific cache.

Examples:

- demographics agent: long-lived cache with data-version invalidation;
- property analysis agent: always execute, but may reuse underlying data snapshots;
- prediction agent: six-hour cache, then recompute;
- education agent: cache static lesson content while retaining personalised progress;
- portfolio recommendation agent: invalidate when portfolio inputs or relevant market snapshots change.

Do not implement cache behaviour as one global switch.

### 10.4 Explainability contract

AI results accepted by the backend should support:

- summary;
- detailed findings;
- source references;
- source timestamps;
- assumptions;
- confidence or quality indicators;
- limitations;
- recommended actions;
- agent version;
- prompt version;
- model identifier;
- data snapshot identifiers.

## 13. Expression-of-interest workflow

This workflow requires strict user control.

### 13.1 Default workflow

```text
New matching listing detected
    ↓
Backend stores listing match
    ↓
User requests or automation creates draft task
    ↓
Backend requests AI-generated draft
    ↓
Draft version stored
    ↓
User reviews and edits
    ↓
User explicitly approves
    ↓
Backend sends through approved email provider
    ↓
Delivery status and replies tracked
```

### 13.2 Safety and governance rules

- Never send an AI-generated EOI without explicit user approval by default.
- Show the exact recipient, subject, body, attachments, and sending identity before approval.
- Validate agent contact details.
- Prevent duplicate EOI sends using idempotency.
- Rate-limit outbound messages.
- Respect unsubscribe, suppression, bounce, and complaint events.
- Store every draft and revision.
- Record approval timestamp and approving user.
- Preserve sent-message content exactly as delivered.
- Support cancellation before dispatch.
- Do not promise contractual commitment unless the user deliberately includes it.
- Make offer amounts, finance clauses, inspection clauses, and settlement assumptions explicit.
- Include configurable disclaimers where appropriate.

### 13.3 Future automation

Any future auto-send mode must be:

- opt-in;
- narrowly scoped;
- revocable;
- legally reviewed;
- rate limited;
- protected by listing and recipient validation;
- fully auditable;
- disabled by default.

Assume at-least-once delivery unless the selected platform guarantees otherwise.

## 17. Database and Alembic standards

### 17.1 Migration discipline

- Every schema change requires an Alembic migration.
- Never edit an already-applied migration.
- Review autogenerated migrations before committing.
- Use deterministic constraint and index names.
- Include downgrade logic when safely possible.
- Separate data migrations from large schema migrations when appropriate.
- Avoid long table locks in production.
- Document irreversible migrations.
- Test migration from empty database to head.
- Test upgrade from the previous production revision.

### 17.2 Constraints and indexes

Use database constraints for invariants such as:

- ownership percentage boundaries;
- positive monetary amounts where required;
- valid date ranges;
- unique provider event IDs;
- unique idempotency keys per scope;
- valid workflow states;
- foreign-key integrity.

Add indexes based on actual access patterns, including likely indexes for:

- tenant and user scoping;
- property timelines;
- active loans;
- transaction dates;
- job status;
- recommendation status;
- webhook event IDs;
- listing matches;
- soft-delete filters.

### 17.3 Soft deletion

Use soft deletion for user-managed records when recovery, audit, or regulatory needs justify it.

Soft deletion must not silently break unique constraints. Design partial indexes or archive strategies appropriately.

### 17.4 Auditability

Record meaningful domain changes, including:

- actor;
- action;
- entity type;
- entity ID;

## 23. Performance and reliability

- Use async I/O for external calls.
- Avoid blocking work in FastAPI event-loop routes.
- Use eager loading intentionally to prevent N+1 queries.
- Apply query timeouts.
- Limit expensive exports and reports.
- Cache only where correctness rules are clear.
- Use bulk operations for imports.
- Paginate timelines and transactions.
- Stream large downloads rather than loading them fully into memory.
- Make Cloud Run instances stateless.
- Do not rely on local filesystem persistence.
- Design for instance termination at any time.

For each expensive endpoint, document expected latency and whether it is synchronous or asynchronous.

## 29. Final operating principles

- Correctness is more important than convenience.
- Never trust client-supplied ownership or user identifiers.
- Never use floating point for authoritative money calculations.
- Never send AI-generated external communications without the configured approval policy.
- Never hide assumptions in a financial calculation or recommendation.
- Never couple the backend directly to one AI or email vendor.
- Never perform long-running work in a synchronous request when a durable job is appropriate.
- Never expose secrets, internal errors, or sensitive payloads in logs or API responses.
- Prefer explicit domain models and workflows over generic CRUD abstractions.
- Preserve history where users need to understand how their portfolio changed.
- Make every important action reproducible, observable, and auditable.
